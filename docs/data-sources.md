# 数据源与发布契约

本文冻结 M0 的业务数据边界。产品只服务当前已公开、已上线内容，**不展示、推断或打包任何未发布数据**。所有外部读取未来都由 Electron Main 进程执行；Renderer 不直接联网。

## 来源分工

| 来源                                       | 可用于什么                                               | 限制与处理                                                                                                                          |
| ------------------------------------------ | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 官方公告与公开规则页                       | 活动名称、开放时间、公开玩法规则、当期公告中的敌人与增益 | 最高优先级的公开规则依据；记录原始链接、抓取时间和生效日期，不把公告之外的推测补成事实。                                            |
| 已认证的米游社战绩数据（Battle Chronicle） | 玩家拥有角色、等级、命座、武器、圣遗物等账号可见资料     | 必须由玩家主动授权；Cookie 仅在 Main 进程安全边界内使用。账号数据只描述玩家，不作为全局玩法规则来源。                               |
| Fandom 文本                                | 已公开玩法或机制的文字补充、人工核对线索                 | 每条采用内容保留页面链接与归属说明，遵守署名与相同方式共享（CC BY-SA）要求。尽量摘取事实并自行表述，不复制长段文本、图片或站点 UI。 |
| `genshin-db`                               | 角色、武器、天赋、敌人等静态公开知识和本地查询索引       | 作为静态知识层；版本固定并记录包/数据版本。不能代替当期官方开放时间或玩家实时账号状态。                                             |
| Enka                                       | 玩家主动提供 UID 后的公开展示柜角色面板                  | **仅限 profile scope**：补充展示角色的等级、武器、圣遗物和数值。它不是完整角色仓库、活动规则、敌人轮换或账号认证来源。              |
| 原始/拆包/数据挖掘来源                     | 开发期间交叉检查字段名、映射和解析器结果                 | **仅开发期 cross-check**，不得进入面向玩家的生产数据包、文案或预测。与已公开来源冲突时不发布，并交由人工复核。                      |

## 现场数据边界

- 只收录官方已公开且已上线的版本、轮换和玩法数据。
- 不提供泄露内容、测试服未发布内容、未来卡池/敌人/活动预测，也不以模糊措辞暗示这类信息。
- “已在客户端文件中出现”不等于“已公开上线”。原始或数据挖掘结果只能帮助开发者发现解析错误。
- 玩家资料与玩法资料分开：米游社/Enka 证明玩家侧状态，官方公告与已审核知识库证明玩法侧规则。

## 字段级来源

每个发布数据包必须包含 `sourceRefs`，每个关键业务字段通过 `fieldProvenance` 指向来源引用 ID。最低记录：

- 来源类型与稳定 ID；
- 可访问时的原始 URL；
- 抓取时间；
- 字段路径与所采用来源；
- Fandom 内容需要的署名说明；
- 人工修正或多来源裁决备注。

同一个对象可以混合来源，但不得只写笼统的“来自网络”。例如活动有效期可来自官方公告，敌人静态抗性可来自固定版本的 `genshin-db`，玩家角色数值可来自米游社或 Enka；三者分别标注。

## 生效日期与版本

- `schemaVersion` 描述结构兼容性；`dataVersion` 唯一标识一份已发布业务数据。
- `effectiveFrom` 必填，`effectiveTo` 可选但不得早于开始时间。
- 轮换数据以明确的生效区间选择，不按下载时间猜测“当前”。
- 推荐计划回显 `dataVersion`，便于复现推荐与审计后续数据变更。
- 时区敏感的活动时间在采集层保留明确偏移或统一为 UTC，并在 UI 按玩家时区显示。

## 人工审核与发布清单

自动采集结果不能直接成为线上数据。发布前至少由一名审核者完成：

1. 对照官方公告确认玩法、时间和当期范围。
2. 对关键敌人机制、资格与复用规则做第二来源交叉检查。
3. 检查字段级来源、Fandom 署名和授权说明。
4. 确认没有未发布内容或受限素材混入。
5. 写入审核人、审核时间，并生成发布 manifest。

Manifest 必须包含数据包 SHA-256 哈希和发布签名。应用加载时先校验哈希与签名；失败的数据包不得进入推荐链路。密钥管理与签名基础设施在后续里程碑实现，M0 schema 先冻结字段。

## 最近可用版本与陈旧行为

已验证的数据包作为 `last-known-good` 保留。新包下载、解析、签名或审核状态异常时：

- 不覆盖最近可用版本；
- 将当前读取状态标为 `stale` 或 `last-known-good`，并展示数据版本和最后审核时间；
- 仍在相同有效期内时，可以谨慎继续推荐，同时在结果中给出警告；
- 已超出生效期时，只能作为旧资料参考，禁止声称它代表当前轮换；
- 没有可验证的最近可用版本时，停止依赖当期数据的推荐，保留玩家本地资料与静态浏览能力；
- 恢复后只有通过完整校验和人工审核的新版本才能替换旧包。

“使用旧资料”是可见的产品状态，不得静默降级。错误日志只记录来源 ID、版本与错误类别，不记录 Cookie、API Key 或 Authorization 内容。
