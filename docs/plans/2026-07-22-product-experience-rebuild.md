# 产品体验与配队链路重构计划

> 日期：2026-07-22  
> 状态：调研完成，等待确认后实施  
> 范围：信息架构、文案、视觉系统、三个挑战玩法、场景数据链路、配队 Agent 与验收体系

## 1. 执行结论

这次不能按“换一套 CSS”处理。当前问题同时存在于四层：

1. 页面把内部实现概念和诊断动作直接暴露给玩家。
2. 推荐页没有消费仓库里已经存在的场景数据，只把手填的敌人英文字符串交给 Agent。
3. 三种挑战玩法被错误压缩成同一种“四人队伍推荐”问题。
4. Agent 没有游戏知识工具，也没有确定性规则校验；本地降级算法只是从面板数值中选前四名。

建议采用“基础系统 + 玩法纵切”的重构方式：先冻结数据契约与视觉方向，再按角色库、深境螺旋、幽境危战、幻想真境剧诗逐条打通完整体验。不要先把所有页面换皮，再回头补推荐逻辑。

## 2. 当前实现审计

### 2.1 信息架构与文案

- 主导航把“账号绑定”当成与角色、配队、历史并列的长期页面；绑定其实只是首次使用和账号管理动作。
- 角色页把刷新、重新登录、连接测试、退出登录、绑定新账号、删除缓存六个动作平铺为同级按钮。
- “米游社 + Enka 融合”“数据完整/部分”“LLM”“fallback”“stage”等是实现语言，不是玩家语言。
- 连接测试、缓存删除、自定义请求头等维护动作占用了默认界面的主要注意力。
- 危险操作缺少明确的二次确认和影响范围说明。

### 2.2 角色库

- `CharacterProfile` 已有命座字段，但角色卡没有展示。
- 角色卡主要靠文字罗列七项面板、武器、天赋和圣遗物，没有建立视觉优先级。
- 所有卡片都使用同一种浅色圆角容器，角色身份、养成状态和可用于配队的关键信号不突出。
- 数据源状态只陈述“融合”，没有解释玩家实际得到了什么：米游社提供完整持有列表，展示柜/Enka 只能补齐有限角色的详细装备面板。

### 2.3 推荐页与场景数据

- 推荐页默认敌人是硬编码的 `abyss-mage, ruin-guard`，界面要求用户自己输入英文 slug。
- 当前“单环境 / 双环境对比”并不是原神里的挑战玩法。
- `scenario:list/get/refresh` IPC 和三种 `ScenarioMode` 已经存在，但 Renderer 没有调用它们。
- 随包场景数据在 2026 年 5—6 月已经过期；默认 manifest 指向的远端仓库当前返回 404。
- 现有幻想真境剧诗类型只允许第 1—8 幕，落后于当前包含第 10 幕和额外挑战的规则。
- 现有幽境危战类型只有一组敌人，无法表达一次挑战的三个阶段/三名首领。

### 2.4 Agent 链路

- 当前运行时明确设置 `tools: []`、`allowedTools: []`，并通过 hook 拒绝全部工具调用。
- DataCurator、TeamComposer、Critique、RotationCoach、Explain 是五次独立文本查询；它们只能依赖序列化进 Prompt 的角色面板与敌人名字。
- 只校验“角色属于玩家、四人不重复、JSON 结构正确”，没有校验玩法资格、元素限制、护盾/免疫、角色职责、队伍循环或跨队抢人。
- Critique 只能淘汰队伍，没有把问题反馈给 Composer 的修复循环。
- 当前“双环境对比”分别生成两次结果，无法联合求解深渊上下半场的角色不重复约束。
- 本地 fallback 只按等级、星级、攻击、生命、双暴、充能、精通排序后取前四名，与敌人和玩法几乎无关。
- 仓库实际依赖是 `@anthropic-ai/claude-agent-sdk`，与部分旧文档中的 “Codex-agent-sdk” 表述不一致，应同步清理文档和命名。

### 2.5 视觉系统

- 背景是多层橙/米/灰径向渐变再整体模糊，没有真实空间、主题叙事或页面差异。
- 品牌、导航、按钮、筛选器、标签大量使用相同胶囊形态；所有内容都落在通用圆角卡片里。
- 1400 多行全局 CSS 同时承担 token、组件和页面样式，导致页面只能不断复用同一种“工业后台”语言。
- UID、数据状态和正文大量使用等宽字，进一步强化开发工具感。
- 当前资源规范正确地禁止直接打包官方角色立绘、UI 切片、音频和商业字体；重构不能为了“像原神”突破这条边界。

## 3. 外部调研结论

### 3.1 三种玩法不是同一个求解问题

| 玩法 | 核心约束 | 推荐结果应该是什么 |
|---|---|---|
| 深境螺旋 | 每层三间、上下半场；两队角色不能重复；同一套队伍要连续覆盖所选房间；敌人波次、护盾、抗性和地脉效果会改变队伍价值 | 同时生成上下半两队，并解释每一间的处理方式、抢人冲突和替补 |
| 幻想真境剧诗 | 当期元素限制、开幕角色、特邀角色、支援角色、难度人数门槛；每名角色有活力消耗；角色与增益获取带有路径和随机性 | 先做“可入场阵容与活力预算”，再给关键幕次的用人优先级和应变策略；不是固定四人队 |
| 幽境危战 | 六档难度；一次挑战含三个阶段、三场限时首领战；高难度有额外机制、限制和明显的首领特攻解法 | 为三个首领分别规划队伍、练度门槛、机制对策和目标难度，并按当期规则处理跨队约束 |

因此，结果模型必须拆成 `AbyssPlan`、`TheaterPlan`、`StygianPlan`，不能继续用统一的 `RecommendationResult.teams[]` 覆盖全部场景。

### 3.2 可用数据源

| 数据源 | 能解决什么 | 不能解决什么 | 采用策略 |
|---|---|---|---|
| 官方 HoYoLAB 公告 | 已公开玩法规则、活动时间、难度说明 | 没有稳定统一的开发者 API，也通常不提供完整机器可读敌人表 | 规则和日期的一等来源；人工或半自动录入 |
| 米游社/HoYoLAB 战绩接口 | 用户自己的深渊、剧诗等历史与进度，可作为个性化信号 | 需要用户 Cookie；不是公开正式 API；不能替代全局当期场景源 | 仅在 Main 进程读取当前用户自己的数据，失败不影响基础功能 |
| Genshin Impact Wiki/Fandom | 已上线玩法规则、赛季/楼层/敌人表和历史页面较完整 | 社区维护；文字为 CC BY-SA，图片许可各异 | 可作为正式服已上线场景的结构化来源之一，只取文字/ID并完整署名，不复用图片 |
| `genshin-db` | MIT；角色、天赋、命座、武器、圣遗物、敌人、多语言静态知识 | 明确不包含活动/赛季数据；Web API 也缺少部分数值函数 | 生成随包的最小化游戏知识快照，供本地规则和 Agent 工具查询 |
| Enka | 玩家展示柜中的角色面板 | 只覆盖展示角色，不提供挑战场景和完整角色机制 | 继续只作玩家面板补全源 |
| Dimbreath AnimeGameData | 可看到 Tower、RoleCombat、Effigy 等原始表，适合研究字段映射 | 新旧仓库均无明确许可证；字段混淆；部分排期由服务端下发；存在未公开内容风险 | 只作开发期交叉核验，不作为发布依赖，不抓取未正式上线数据 |
| HomDGCat 等资料站 | 人工核对当前敌人和机制很方便 | 无稳定公开 API/许可，且可能混入测试服或未发布内容 | 不接入生产链路 |

结论：公开数据足够启动，但不存在一个可直接依赖的统一官方 API。需要单独维护一条规范化发布链路；这正好可以落到当前代码已经预留、但尚不存在的 `genshin-team-advisor-data` 仓库。

### 3.3 数据链路原则

1. 只收录正式服已经公开/上线的内容，不收录测试服、解包未来内容或泄露信息。
2. 每个字段保留 `sourceUrl`、`sourceType`、`collectedAt`、`effectiveFrom`、`effectiveTo` 和人工审核人。
3. 官方公告优先；社区资料作结构化补充；来源冲突时阻止发布而不是静默覆盖。
4. JSON Schema/Zod 双重校验，生成内容经 PR 审核后才进入 manifest。
5. manifest 带版本、SHA256、数据有效期和最低 App schema 版本。
6. App 使用 last-known-good；过期数据必须显示“数据更新于某日”，不能继续冒充“本期”。
7. 图片不进入该数据仓库；敌人和角色只使用 ID、名称与自有图形占位。

## 4. 目标产品结构

### 4.1 全局导航

主导航只保留三个玩家任务：

1. **我的角色**：检查角色和养成数据。
2. **挑战配队**：选择三种挑战并生成方案。
3. **推荐记录**：回看、比较和继续调整旧方案。

账号切换、绑定新 UID、语言与设置放到固定的账号菜单；首次没有账号时才进入绑定向导。Settings 不再与核心玩法争夺视觉中心。

### 4.2 角色库头部

目标结构：

- 左侧：昵称、UID、世界等级和当前账号切换器。
- 中部：一句玩家语言的数据摘要，例如“已读取 112 名角色，其中 8 名有完整装备面板”。
- 右侧：唯一主按钮“更新角色数据”。
- 次级入口“账号与数据”菜单：切换米游社账号、绑定新 UID、退出登录、连接诊断、删除本地数据。
- “数据说明”折叠层解释：米游社负责角色名单，展示柜负责部分角色的装备面板；不在主界面展示 Enka 等技术词。

删除数据必须显示 UID、会删除的内容和不可恢复提示；连接测试只在诊断页出现。

### 4.3 角色卡

信息分三层：

1. **身份层**：名称、等级、命座、元素类别、稀有度、面板完整状态。
2. **配队层**：推导角色定位、主要反应标签、当前武器、关键充能提示。
3. **详情层**：展开后查看七项数值、天赋、圣遗物主词条和来源说明。

图形策略：

- 攻击、生命、防御、双暴、充能、精通、武器、天赋、圣遗物使用自绘通用 SVG 图标。
- 元素使用语义明确但与官方图标轮廓不同的自绘符号。
- 稀有度可用星形，但造型和排布不复刻游戏 UI。
- 在当前版权约束下，不直接打包或改造官方角色头像、元素图标和游戏 UI 切片。角色视觉先使用原创元素纹理、剪影/字标和稀有度边框；未来若取得明确授权，再通过独立媒体适配器替换。

### 4.4 挑战配队首页

页面首先展示三个大型玩法入口，而不是输入框：

- 深境螺旋：显示当期时间、最高层、上下半缩略信息。
- 幻想真境剧诗：显示当期元素、可用人数/要求人数、开幕与特邀角色。
- 幽境危战：显示当期三名首领、推荐目标难度和剩余时间。

用户进入玩法后再选择难度/楼层/目标，不再手输敌人名称。高级用户可以在“自定义演练”里手动组场景，但该功能不占默认流程。

### 4.5 三种玩法页面

#### 深境螺旋

- 选择楼层或指定房间；默认读取当前周期。
- 用上下半两列展示敌人波次、护盾/免疫和关键机制，全部使用本地化名称。
- 玩家偏好改为可理解的 chips：操作简单、生存优先、低练度、尽量不用五星武器、保留某角色。
- 一次联合生成两队，自动避免重复角色；允许锁定/排除角色后只重新计算受影响的半场。
- 结果按房间说明“为什么能打”“最容易超时在哪里”“有什么替换位”。

#### 幽境危战

- 先选目标难度，再并列展示三个阶段和各自的首领机制。
- 为每个阶段分别给队伍和开局循环；规则中的能量、时间、增益和跨队限制来自场景数据，不写死在 Prompt。
- 明确区分“拿原石即可”“冲高难奖励”“挑战 Dire”等目标，避免默认把普通玩家推向不现实的练度要求。

#### 幻想真境剧诗

- 先做资格检查：当期元素、可用人数、等级、开幕/试用/特邀/支援角色。
- 输出不是三套固定队，而是“入场角色池 + 角色活力预算 + 关键幕次保留策略 + 增益选择优先级”。
- 对随机事件给分支建议；无法保证的结果要明确标为条件策略。
- 若角色池不够，先告诉玩家缺多少人、最值得补哪几个低成本位置，不调用大模型假装能通关。

### 4.6 历史与设置

历史页：

- 按玩法和周期分组，卡片显示“深境螺旋 12 层”“幻想真境剧诗 2026-07”等玩家语义。
- 保存 `scenarioId/schemaVersion/dataVersion`，历史结果不因当前数据更新而改变含义。
- 支持“基于这次方案重新计算”，而不是堆叠范围、来源、关键字、日期等后台筛选器。
- 删除单条和批量删除都有二次确认。

设置页：

- 默认只显示 AI 服务连接状态、当前模型、隐私说明和数据更新时间。
- Base URL、模型名、自定义 Header、连接诊断放到“高级设置”。
- API Key 只显示“已保存/未配置”；不使用 LLM、BYOK 等术语作为主要文案。
- 数据管理集中展示角色缓存、场景缓存、历史记录的大小和删除影响。

## 5. 视觉与素材方向

### 5.1 设计原则

- 目标是“提瓦特式冒险手册的轻盈、精致与空间感”，不是复刻任何一张游戏界面。
- 背景以冷蓝灰、云雾青和石墨蓝建立空间，象牙白作为阅读面，低饱和金只用于边线和状态强调。
- 减少大面积暖橙渐变、通用圆角卡片和胶囊按钮。
- 主按钮使用自有的轻斜切/折角轮廓、双层细边和克制的呼吸光；次级动作保持文字化。
- 面板使用轻薄材质、内外双线和自绘角饰，不做厚重阴影悬浮卡片墙。
- 标题使用 OFL 的中文展示字体，正文保持高可读无衬线；等宽字体只用于 UID、版本号和调试值。

### 5.2 需要生成/制作的素材

在视觉方向确认后再生成，避免先产出一批无法统一使用的图片：

- 全局原创高幻想远景背景：无角色、无官方地点、无 Logo、无官方 UI 构件。
- 三种玩法各一张低对比场景底图：深渊星穹/遗迹、剧诗舞台/书页、危战风暴/岩场，仅表达气氛。
- 空状态插画：未绑定账号、数据同步失败、角色池不足、暂无历史。
- 自绘 SVG：导航、数据状态、七项面板、玩法标识、卡片角饰、分隔纹样。

所有位图输出 2560×1600 主版和 1600×1000 轻量版，转为 WebP/AVIF；每项资源记录生成提示、作者/工具、日期和使用范围到 `resources/credits.md`。

### 5.3 动效

- 页面切换 180—260ms，使用透明度、少量位移和遮罩揭示。
- 背景只做极慢的 2—4px 视差，不做持续炫光或粒子雨。
- 推荐过程显示玩家语义步骤：“读取角色 → 分析挑战规则 → 生成队伍 → 检查冲突 → 整理打法”。
- 支持 `prefers-reduced-motion`；不把动画作为状态的唯一表达。

## 6. 推荐系统重构

### 6.1 新输入上下文

`AdvisorPlanInput` 至少包含：

- `mode`、`scenarioId`、`dataVersion`、目标楼层/难度/幕次。
- 完整 `ProfileBundle` 与明确的数据缺口。
- 本地游戏知识：角色定位、元素附着、能量需求、关键天赋/命座、武器类型、治疗/护盾/聚怪等能力标签。
- 场景知识：敌人波次、护盾、抗性、免疫、特殊机制、时间目标、地脉/玩法 Buff。
- 模式规则：允许角色范围、跨队复用、连续房间、活力、试用/支援角色等。
- 玩家干预：锁定、排除、偏好、生存要求、目标奖励、是否愿意换装备。

### 6.2 只读业务工具

保持 Bash/Edit/WebFetch 等原生工具关闭，但给 Agent 注册主进程内的只读业务工具：

- `get_scenario(mode, scenarioId, nodeId)`
- `get_character_kits(characterIds)`
- `get_enemy_mechanics(enemyIds, difficulty)`
- `get_reaction_rules(elements)`
- `evaluate_team(team, context)`
- `get_player_challenge_history(uid, mode)`（有授权数据时）

这些工具只查询经过校验的本地数据库/JSON，不允许 Agent 自己联网或读任意文件。每次调用记录耗时、版本和已脱敏参数。

### 6.3 决策流水线

1. **Context Builder（确定性）**：合并玩家、场景、规则和偏好，标记缺失数据。
2. **Candidate Generator（确定性）**：按硬约束生成可行角色池和候选队伍/演员池。
3. **Team Composer（模型）**：在候选中做权衡，输出结构化方案和明确假设。
4. **Rule Validator（确定性）**：校验角色资格、重复、元素限制、职责覆盖、机制要求、活力预算等。
5. **Critique（模型）**：只检查软风险、循环与实战容错。
6. **Repair Loop**：Validator/Critique 失败时把具体 issue 返回 Composer，最多修复两轮；不能修复则保留可行部分并说明原因。
7. **Rotation Coach / Explain**：只处理通过校验的方案，生成打法和玩家文案。

### 6.4 干预机制

- 玩家可以锁定/排除角色、拖换单个位置、标记“不想换圣遗物”、选择目标奖励。
- 每次重新生成只重算受影响部分，并保留其他队伍。
- 结果展示“硬性限制、选择理由、主要风险、可替换位、数据置信度”。
- 本地记录“采纳/不适合”及原因，用于后续同一账号的偏好排序；默认不上传。
- 如果场景已过期或关键规则缺失，停止声称“本期推荐”，改为只读旧数据或自定义演练。

## 7. 实施里程碑

### M0 — 冻结产品与数据契约

产出：

- `docs/challenge-modes.md`：三种玩法规则、推荐目标、输入输出契约。
- `docs/data-sources.md`：来源、许可证、更新频率、降级和正式服数据政策。
- `docs/design/product-language.md`：玩家文案词典与禁止暴露词。
- `src/shared/scenario-v2.ts`：三种独立场景和计划类型。
- schema fixture 与契约测试。

验收：旧的 `enemyNames: string[]` 不再是新推荐入口；所有场景实体都能携带版本、有效期和来源。

### M1 — 启动独立场景数据链路

建议此里程碑单独开一个 Codex session，在预留的 `genshin-team-advisor-data` 仓库完成：

- 正式服 live-only 数据录入/转换器。
- Fandom/官方公告适配器和人工覆盖文件。
- 三种玩法当前与历史 fixture。
- schema 校验、来源差异检查、PR 审核和 manifest 发布。
- App 端 last-known-good、过期状态和数据版本迁移。

验收：manifest 可用；三种数据结构能表达当前规则；来源 404、过期、字段冲突都有自动化测试。

### M2 — 视觉基础与应用壳

修改范围：

- 拆分全局 CSS 为 reset、tokens、primitives、layout 和 page modules。
- 新建按钮、面板、菜单、状态条、对话框、玩法入口等基础组件。
- 重做主导航和账号菜单，移除绑定页的常驻导航位置。
- 生成并接入经确认的全局背景与三种玩法背景。
- 建立字体、SVG、位图和 credits 流程。

验收：1024×768 到 1600×1000 无横向溢出；键盘可达；正文对比度达 WCAG AA；无官方素材进入仓库。

### M3 — 角色库与绑定体验

- 合并账号概览和同步状态。
- 只保留一个主操作；维护/危险动作进入菜单和确认框。
- 重构角色卡的信息层级，补齐命座和语义图标。
- 把技术数据源文案改为玩家可理解的覆盖说明。
- Onboarding 改为“选择获取方式 → 登录/UID → 选择账号 → 首次同步”的短向导。

验收：新玩家不需要理解 Enka、Cookie 或缓存即可完成绑定；角色库默认首屏能回答“我有谁、数据是否够用、下一步做什么”。

### M4 — 深境螺旋纵切

- 先接入最成熟的上下半联合优化。
- 新建场景选择器、敌人波次卡、两队结果和角色锁定/排除交互。
- 接入本地知识工具、确定性 Validator、修复循环和玩法型 fallback。
- 历史记录升级为带周期/楼层/房间的数据。

验收：上下半零重复；零英文 slug；所有敌人均能追溯来源；每个硬约束错误都有测试。

### M5 — 幽境危战纵切

- 扩展为三个阶段/三名首领和六档难度。
- 加入首领机制、能量/时间目标、目标奖励和三队联合资源提示。
- 针对高难度给练度门槛和“不建议继续冲”的诚实反馈。

验收：三个阶段均有独立方案和机制依据；不同难度不会复用错误规则。

### M6 — 幻想真境剧诗纵切

- 实现资格检查、演员池、活力预算、幕次路径和随机事件策略。
- 允许开幕/试用/特邀/支援角色，且明确其来源和可用性。
- 输出计划型 UI，不套用普通四人队结果卡。

验收：所有元素、人数、等级和活力硬约束由确定性代码校验；角色不足时给建设建议而不是生成无效队伍。

### M7 — 历史、设置与文案收口

- 历史按玩法/周期重组并支持基于旧方案重算。
- Settings 拆成常用与高级；诊断和数据管理集中。
- 全量扫描并移除面向玩家的内部词、英文 slug、内部 stage ID。
- 增加错误状态、空状态和离线状态插画。

验收：默认界面不出现 `Enka`、`LLM`、`fallback`、`partial`、`stage` 等内部词；所有危险动作均有确认。

### M8 — 质量门禁

- 三种玩法各建立真实规则 fixture 和 golden constraint 测试。
- Agent eval 只评估硬约束、实体有效性、依据覆盖与解释一致性，不把固定“标准答案队伍”当唯一真值。
- Playwright 覆盖首次绑定、角色同步、三种推荐、锁定/排除、历史重算、设置与离线降级。
- 增加 1024×768、1280×800、1440×900、1600×1000 截图回归。
- 完成键盘、焦点、屏幕阅读器标签、减少动态效果和色弱可辨识检查。

发布门槛：

- 硬约束违规率 0。
- 未知角色/敌人 ID 率 0。
- 当期数据过期时绝不显示为“最新”。
- Renderer 外部网络请求 0。
- 官方图片/UI/字体直接入库 0。
- `lint + typecheck + unit + build + e2e` 全通过。

## 8. 推荐执行顺序与决策点

推荐顺序：M0 → M1/M2 → M3 → M4 → M5 → M6 → M7 → M8。

原因：

- M0 先冻结三种结果结构，否则数据仓库、Agent 和 UI 会重复返工。
- M1 与 M2 可以在契约冻结后并行推进，但 M4 之前必须有可信场景数据。
- 深境螺旋是最适合验证“双队联合求解”的第一条纵切。
- 幽境危战复用多队框架，但增加首领机制和难度。
- 幻想真境剧诗不是普通配队问题，数据和交互最复杂，应在基础求解与工具稳定后完成。

实施前只需要确认一个产品决策：继续遵守当前“官方角色立绘、元素图标和 UI 切片不直接入库”的版权边界。本文默认继续遵守，并以原创图形与生成背景完成主题化；若要改变，必须先单独做授权与法律评估，不能在视觉重构中顺手混入。
