# 幽境危战根规格闭环设计

## 目标

关闭 M5 根规格审查中的五个缺口：让三阶段本地求解在完整角色库上保持同步有界；把奖励目标与难度约束变成正式产品策略；让智能修复轮独立取证；拒绝语义损坏的历史快照；所有挑战修正经过玩家安全的中文本地化。

## 决策

### 1. 有界三阶段求解

采用 M4 已验证的“先可行、后优化”模式，不在完整角色库上枚举四人组合。

1. 先把三个阶段的护盾、免疫和已知能力要求编码为硬约束位图。
2. 通过按角色递进的动态规划构造 12 个队伍槽位；状态键只保留每阶段人数、覆盖位图、锁定覆盖和跨队出场计数。状态超过预算时返回 `budget-exceeded`，完整搜索无解才返回 `infeasible`。
3. 可行种子首先进入候选池，随后加入每阶段硬机制专才，并按每阶段评分轮询补足到 20 人硬上限。`forbidden` 的 12 名不重复可行种子天然能完整保留。
4. 只在至多 20 人的池上构造四人队候选，并对每阶段候选数设置硬上限；联合搜索继续使用状态预算和确定性 tie-break。

性能验收覆盖 14、38、80 名角色。角色库扩大不能把已有可行结果变成预算耗尽或不可行；添加无关高分角色不能挤掉唯一硬机制解法；单次同步求解需低于测试中明确的 1 秒阈值。

### 2. 奖励目标—难度策略

这是产品意图，不宣称官方奖励阈值：

| 目标 | 最低难度 order |
|---|---:|
| 拿原石即可 | 1 |
| 冲高难奖励 | 5 |
| 挑战极限难度 | 6 |

共享策略模块是 UI、validator 和本地评估的唯一真相源。UI 切换目标时自动把难度抬到最低允许档；服务边界仍拒绝矛盾输入，避免绕过 UI。

弱证据建议必须满足 `targetMin <= suggestedOrder < selectedOrder`。如果玩家已经位于目标最低档，则不返回 `suggestedDifficultyId`，而明确提示降低奖励目标。`high-reward` 使用比 `primogems` 更严格的证据要求，确保它实际影响推荐结论。

### 3. 修复轮独立取证

首轮和修复轮分别生成 `round: compose | repair` 的审计记录。每轮 required-tools 校验只接收该轮的工具记录；修复轮必须重新成功读取一次 profile、三个阶段，以及覆盖最终所选角色的 knowledge。首轮工具不能为修复轮补齐缺失项。业务工具日志同时记录 correlation 和 round。

### 4. 历史语义深验

历史记录在结构校验后执行 entry 级语义校验：

- 三队各恰好 4 名角色且队内不重复；
- 每个计划角色都有唯一、非空的 owned name snapshot；
- 实际出场次数符合 `forbidden / limited / allowed`；
- 所有 locked 均出现，所有 excluded 均不出现；
- plan 的场景身份、复用声明与 history 元数据一致；
- intervention target 与记录 target 一致。

任何失败记录在读取时丢弃，不返回 IPC，也不进入 Renderer。

### 5. 玩家安全修正文案

新增单一纯函数 `localizeStygianModifier`：

- 含自然中文且不含内部键的文案原样保留；
- 已知 key 映射到稳定中文；
- 任意英文句、slug、内部 key 统一显示“挑战修正暂无中文说明”；
- fallback 仍表示存在未知修正，不把未知当作无修正。

业务工具、Agent payload、本地 optimizer guidance 与 Renderer 都使用该函数。发布层继续允许签名 raw modifier；玩家结果契约只接收本地化后的安全文本。

## 错误与验证

- 搜索预算耗尽与确证无解使用不同 issue。
- 目标难度冲突使用独立结构化 issue。
- 修复轮缺少工具导致智能方案失败并回退本地规则。
- 损坏历史被隔离，不尝试“猜测修复”。
- modifier 的 raw 数据合法性与展示安全性分层处理。

验证顺序：每项先写失败测试并确认失败，再做最小实现；跑聚焦测试、全量单测、lint、typecheck、build、Electron E2E，最后由原 reviewer 和根规格 reviewer 复审。
